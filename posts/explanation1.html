[Explanation1] Emade에서 판매자는 어떻게 상품을 올릴까

Emade 팀 · 2026-11-30 · 2026 오픈SW플랫폼 팀 프로젝트

이 글은 판매자 편이다. 구매자가 상품을 찾고 사고 리뷰를 남기는 흐름은 구매자 편에서 다룬다.

Context

Emade는 이화여대 학생들이 직접 만든 취미 작품을 사고파는 교내 마켓이다. 프론트엔드는 React + Vite, 백엔드는 Flask, 데이터는 Firebase Realtime Database를 쓴다. 이 글에서는 판매자가 가입해서 첫 상품을 올리기까지의 흐름을 살펴본다.

Problem / Goal

Emade는 캠퍼스 안 직거래만 가능하고, 판매자와 구매자가 메시지를 주고받을 수 없다. 그래서 판매자가 만날 시간과 장소를 미리 정해 두고, 구매자는 그중 하나를 골라 바로 예약하는 구조가 필요했다.

Steps

1. 회원가입 · 로그인

이화여대 이메일(ewha.ac.kr, ewhain.net)로만 가입할 수 있다. 프론트에서 도메인을 검사해 칸 아래에 에러 문구를 보여 주고, 서버도 가입 요청을 받을 때 같은 검사를 한 번 더 한다. 로그인은 Flask 세션(쿠키) 방식이다.

2. 거래 일정 설정 — 상품보다 시간이 먼저

판매자는 마이페이지 > 나의 거래 일정에서 매주 반복되는 거래 가능 시간을 30분 단위로 정하고, 달력에서 특정 날짜만 막을 수도 있다. 처음에는 예외 시간을 상품마다 정하게 했지만, 시간이 안 되는 것은 판매자 본인의 사정이라서 판매자 단위로 옮겼다.

주간 시간이 없으면 상품을 등록할 수 없다. 시간이 없는 상품은 구매자가 예약할 수 없기 때문이다. 그래서 상품 등록 화면은 들어오자마자 이를 확인한다.

// pages/product/ProductReg.jsx (핵심만 발췌)
getMySchedule().then((schedule) => {
  if (!hasWeeklySchedule(schedule)) {
    alert(NO_SCHEDULE_MESSAGE);   // "거래 가능한 주간 시간을 먼저 설정해 주세요."
    navigate(SCHEDULE_PAGE, { replace: true });   // → /mypage/schedule
    return;
  }
  setReady(true);   // 확인이 끝나야 입력 폼을 보여 준다
});

일정이 없으면 안내창을 띄우고 거래 일정 화면으로 보낸다. 서버도 SCHEDULE_NOT_FOUND 에러로 한 번 더 막는다.

3. 상품 등록 — 거래 장소를 자세히

상품 등록 화면은 왼쪽 입력 폼(사진, 상품명, 카테고리, 가격, 재고, 설명, 거래 장소, 태그)과 오른쪽 미리보기 카드로 나뉜다.

가장 고민한 부분은 거래 장소다. 처음에는 "학문관"처럼 건물을 고르게 하려 했지만, 메시지를 보낼 수 없으니 건물 이름만으로는 어디서 만날지 알 수 없다. 그래서 판매자가 장소를 직접 자세히 적는 방식으로 바꿨다. 장소는 여러 곳을 추가할 수 있고, 같은 장소를 두 번 넣으면 에러 문구를 보여 준다.

등록하기를 누르면 사진과 함께 FormData로 보낸다. 서버는 상품을 저장하면서 판매자별·카테고리별·태그별 목록도 함께 만들어 나중에 빠르게 찾을 수 있게 한다.

Result

판매자는 가입 → 일정 설정 → 상품 등록만 하면 구매자가 예약할 수 있는 상품을 만들 수 있다. 구매자는 메시지 없이도 판매자가 정한 시간과 장소 중 하나를 골라 바로 예약한다.

What I learned

판매자 흐름을 구현하면서 화면의 입력 순서와 데이터 검증 순서는 반드시 같을 필요가 없다는 점을 배웠다. 사용자는 상품 등록을 시작하기 전에 거래 가능 시간을 먼저 준비해야 하며, 서비스는 이 조건을 화면과 서버에서 모두 확인해야 한다. 이렇게 하면 잘못된 예약 데이터를 줄이고 구매자에게도 일관된 정보를 제공할 수 있다. 이 기준은 이후 기능을 추가할 때도 판매자와 구매자의 흐름을 안전하게 연결하는 출발점이 된다.

  • 데이터가 누구에게 속하는지부터 정해야 한다. 예외 시간을 판매자 단위로 옮기면서 등록 폼이 단순해졌다.
  • 같은 검사는 프론트와 서버 양쪽에서 한다. 프론트 검사는 사용자가 빨리 알아차리게 하고, 실제로 막는 것은 서버다.
  • 채팅이 없다는 제약이 UX를 바꿨다. 대화로 해결할 수 없으니 처음 입력하는 정보가 자세해야 했다.
